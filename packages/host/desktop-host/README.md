# dsh-desktop-host

English | [中文](README.zh.md)

## Summary

The machine-local DSH Host serves Desktop Main. It keeps issuer-qualified Person Profiles outside Slark environments, serializes same-session commands, fences approvals and environment context leases, supervises isolated Profile workers, and exposes an owner-only authenticated Unix socket. The Host control component owns no HTTP listener. Its composition starts the existing `dsh web` worker, exchanges the one-use launch URL itself, and returns only a verified loopback origin plus an HttpOnly cookie name/value to trusted Main; neither the launch token nor a filesystem path reaches Renderer. Bootstrap redirects must be exactly `/` or `./`; other redirect targets are rejected before cookie use.

## Desktop adapter

Remote UI boot reads project the worker's document-relative `plugins/` references to the Host root route `/plugins/` in the returned injection table. The worker's local Web document keeps its relative references; remote asset reads still require an exact boot-listed URL and the active view lease.

The pinned native helper creates its default loader only after validating the exact addon path and bytes. Importing that helper does not resolve a native package. The private `windows-startup.js` composition passes the same release pin to its parent SID, registration, listener, and cancellation adapters and includes it in strictly decoded Worker boot data. The file Worker independently revalidates and loads that exact addon for cancellation, pipe I/O, lifecycle, and peer attestation. Neither production path searches the Koffi package; the embedding must still verify release metadata and protect the installed files throughout use.

Windows directory security evidence preserves generic, standard, and file-specific SDDL rights as unsigned masks. Unknown tokens and masks wider than 32 bits reject inspection. Parsing generic rights does not grant private-storage access: private files still require the exact protected three-principal file-full-control DACL.

The startup artifact exposes `loadWindowsLegacySourceProbe` for trusted embedding code. Assembly resolves the current process SID through the same release-pinned native addon as local-vault storage, performs no legacy filesystem inspection, and returns only a read-only probe. Unsupported platforms, missing pins, native identity failures, or a missing directory inspector reject loading. The embedding must protect the addon throughout later probe calls and supply the OS-selected user home.

The Windows native directory inspector reads existing-path attributes and security evidence without creating directories or repairing permissions. Missing paths, denied access, sharing conflicts, and inspection failures throw. Its evidence does not authorize migration or prove ancestor safety after the read handle closes; complete legacy inventory remains separate.

The legacy-home metadata probe distinguishes an observed missing `.dsh` leaf from an existing directory or an unknown result. It inspects ancestors first, rejects redirected paths and foreign user-home ownership, and treats empty existing homes as present without reading their contents. Only the native leaf-open file-not-found error produces observed absence; no result admits migration or replacement creation. Source enumeration, schema checks, and stable-tree verification remain required.

`discoverUnixHost` reports `running`, `stopped`, or `unknown`. Only a registry-owned endpoint with no listening process is `stopped`; failed UID, installation-key, executable-signature, challenge, frame, or socket-shape verification is `unknown`.

Windows local Profile storage accepts embedding-encrypted envelopes up to 16 KiB. It reuses native SID/DACL and reparse checks, requires a verified file lease for replacement, and releases the lease after synchronous callbacks, including failures. Missing files return null; permission and integrity failures do not authorize a new identity. Native assembly requires one canonical, singly linked Koffi addon and its independently release-verified SHA-256; it never searches alternate packages or paths. The embedding owns encryption, environment-root selection, and protection against addon replacement throughout loading and use. Digest checks alone do not prove Windows installation ACLs or publisher signatures; native installation validation remains required.

The Windows client uses a private file-backed Worker to attest the connected pipe server before sending Host frames. Its Bun Main cancellation adapter is supplied by this package through the verified client artifact; callers provide the release-pinned Worker and publisher anchors. Worker exit must be confirmed before its transferred thread handle is closed. Windows distribution remains subject to signed-carrier and native installation validation.

Windows Host startup converts canonical absolute Worker paths with Windows file-URL rules, preserving Unicode, spaces, literal percent signs, and hash characters in installation directories.

Client cancellation retains a thread handle transferred after startup cancellation. If the cancellation retry budget expires, the parent retains the handle until a later normal or failed Worker exit confirms it can be closed; exhausting the budget does not prove shutdown.

`UnixHostClient` exposes Profile account ensure/restore/status/open, local bootstrap/restore/open, view-activation/close, and owner-only migration operations. The local operations accept no account identity, token, binding, or environment assertion; the Host selector plus Keychain material restores the local-only Profile on a later authenticated connection. Reopening the same Profile from its authenticated owner atomically extends the existing short-lived view lease and issues a fresh one-use activation handle, so an active Desktop can renew authorization without replacing its renderer. The `profile.ensure_account_token` capability marks a Host that accepts the token-bearing `profile.ensure` payload; either peer reports `upgrade_required` before mutation when that capability is absent. `profile.ensure` requires a short-lived canonical DSH Account token with the `dsh-host` audience; the Host verifies it offline and requires its issuer and subject to match the requested account before any Profile registry mutation. Every operation accepts an `AbortSignal`. Aborting destroys the authenticated connection, and the Host revokes every view lease and Profile unlock reference owned by that connection. Another staging or production connection that independently proved the same Profile retains its own view lease when either connection reopens the Profile; expiry, connection loss, and Profile revocation still invalidate the affected leases.

The connection starts with `host.inspect`: Desktop supplies a fresh challenge and verifies the installation Ed25519 signature, trusted installation id and key, peer UID, executable signature digest, Host process nonce, and runtime generation. Later frames repeat the client, Host, and process identities and carry a 30-second-bounded single-use JTI.

## Profile and execution authority

`profile.workspace_model_selection` resolves the Profile from this connection’s token-verified Account binding and rechecks it after reading. The supervisor discards replies from disposed or replaced workers. macOS and Windows startup install the reader; older Hosts omit its capability. A separate random worker token authorizes the private HTTP endpoint, whose complete response is bounded while streaming. The request refuses redirects to preserve the attested listener. The 15-second deadline covers both the request and complete response read; completion rechecks cancellation before admitting the result. The result does not authorize Source registration, planning or task execution.

`profile.workspace_authority` uses the same authorized reader to issue an installation-signed membership statement without opening a view, appending a Session event or sending a model request. Its client verifies the exact challenge, current installation/process, expiry and signature. Missing readers omit the capability. The server-side nonce, consumption and Source checks remain separate; see [the protocol](../control-protocol/README.md#challenge-authentication).

`profile.collaboration_registration` uses the connection’s verified Account grant and installation private key to sign the server challenge together with the current Host process. The client verifies the signature against its inspected installation, checks every challenge/process field and expiry, and returns a frozen assertion. Unix and Windows share this authority/client method. It does not start a worker, open a view lease or mutate Profile/Session data. Slark’s private Host broker owns the separate connection and cancellation; server challenge persistence, key registration and operation reconciliation remain outside this method.

Existing-only preflight accepts the exact current worker patch or the released `settings` owner layout, with every persistence, storage, credential, and settings path still bound to the inspected generation. It does not rewrite either layout during inspection. Worker startup selects the current `config-editor` owner layout after authorization; changed or redirected released patches remain rejected.

Desktop model text requests require a token-verified connected Account grant owned by the requesting Host connection. The Host checks that grant before and after the worker call without changing the visible Profile view lease, forwards cancellation, and returns only a classified failure or bounded text. Each worker receives a random private token for its local endpoint; ordinary browser cookies cannot authorize that endpoint.

Remote Session execution is an optional Host dependency. When installed, `profile.remote_session` is advertised and accepts only the control protocol's closed command union through a live owner-bound view lease. The Host resolves the Profile from that lease, forwards connection cancellation, rechecks the same lease after the awaited executor call, and validates the bounded result through the canonical wire codec before returning it. Hosts without the executor omit the capability, and the client returns `upgrade_required` without sending a command. This seam does not expose browser cookies, launch tokens, Profile paths, or a generic HTTP proxy.

Remote Web DSH reads use `profile.remote_ui_read` with the same owner-bound lease checks before and after the worker call. macOS and Windows Host startup install the exact-endpoint worker executor; the worker's private bearer token stays inside the Host. For `asset/read`, the Host checks the current boot injection table, fetches only a listed same-origin `/plugins/` script with its private cookie, requires a JavaScript response, caps the complete asset at 8 MiB, and returns 24 KiB chunks from one worker-local cache. The control frame rejects responses above 64 KiB. This is a bounded read seam, not a stream or general Web API tunnel.

The Profile worker handle reads its private `session/follow`, `workspace/follow`, or `$events` NDJSON route. It accepts only bounded item frames followed by an explicit end, cancels the HTTP reader on caller disposal, and rejects malformed, failed, or incomplete streams. The Host exposes this reader only through `profile.remote_ui_stream`: each short open, poll, or close request checks the owner-bound lease; the connection owns at most eight cursors; each cursor buffers at most one 512 KiB event and returns 16 KiB chunks without blocking the control channel while idle. The next request after lease revocation, or connection loss, cancels its reader. No worker token or general Gateway stream crosses the control channel.

Account provisioning preserves the exact prior registry row when worker preparation fails, including an issuer or subject replacement. A concurrent registry change prevents rollback and returns `stale`. A missing worker provider rejects before registration. These rules affect registry metadata only; they neither authorize a cloud identity migration nor move or delete Profile content.

Adding an account binding after restoring a row without the optional binding field writes the canonical registry field order, so the updated row remains readable after Host restart.

The Profile registry stores an opaque Profile id, opaque Keychain handle, and domain-separated unlock verifier for every Profile. Account Profiles also store a device-keyed HMAC of canonical DSH Account issuer plus opaque subject and environment-scoped current binding handles and versions; staging and production bindings for the same person resolve to one account Profile. Local-only Profiles use a device-keyed random index and never gain an account binding. A higher server-signed binding version atomically replaces only that environment's old account handle and invalidates older signed selectors. An Account issuer replacement preserves the existing Profile only when the request carries that same environment binding handle, a strictly higher version, the same Keychain handle, matching unlock material, and a valid token for the replacement identity. Raw account identity and the 32-byte Main-vault unlock material are absent from the file, and successful constant-time verification authorizes only the current authenticated connection.

`profile.ensure` returns a Host-signed opaque selector bound to the installation, Profile, binding generation, runtime generation, and schema generation. `profile.restore` accepts that selector, the exact Keychain handle, and fresh Main-vault material. Copying a selector to another installation, replaying it after a binding rotation, guessing a handle/material, or disconnecting the proving connection fails closed.

The macOS startup composition validates owner-only non-symlink roots, starts exactly one Host, checks the Node executable and fixed DSH entrypoint independently, verifies the Account public keyring against the embedding release's SHA-256 pin, performs native peer PID/executable/code-signature attestation, and publishes the exact secret-free `~/.dsh/host/registration.v1.json` discovery record. After acquiring exclusive Host ownership, a runtime upgrade may atomically refresh only that record's executable signature digest; every installation, key, endpoint, and socket field must remain identical. Profile workers inherit no ambient environment. The Host verifies the child owns its reported loopback listener, exchanges its one-use launch token for a signed cookie, confirms unauthenticated `/` is 401 and authenticated `/` is 200, then discards the token.

Offline Account recovery starts declared plugins only when each top-level dependency resolves through the current packaged runtime or a digest-verified Profile compatibility closure. A Profile-contained flattened dependency tree is reported as runtime-incompatible and retained for read-only export; the Host does not infer compatibility from readable files or a lockfile.

Command writes serialize by Profile and Session, while different Sessions can proceed concurrently. The fsync-backed journal records `started` before execution and a committed outcome afterward; a crash between them recovers as `unknown`, never success. Approval decisions compare payload hash, decision version, window generation, and expiry. Environment context attaches to a Session lease and never becomes Profile-global state.

The extension-operation owner prepares short-lived Profile-bound plans and persists metadata-only receipts before executor effects. A live view lease and writable Profile grant authorize the target through `DesktopHost.authorizeExtensionView`; callers must recheck that authority before every mutation. Same-Profile writes serialize, duplicate confirmations cannot create another operation, and cancellation remains a request until the executor settles. Unfinished receipts recover as `unknown` and block further writes to that Profile; they are never replayed automatically. Executors must settle only after their subprocesses and writes stop. The Host process lock must remain held until operation disposal completes.

The MCP executor reuses the pinned Desktop Hub parser and AST merge in [hub-upstream](hub-upstream/UPSTREAM.json), preserving unrelated rows, comments, and environment references. It atomically writes only the Host-resolved Profile's `profiles/web/cordis.patch.yml`, then restarts that worker and checks the authenticated `pluginInventory/list` response. Installed rows use `failOnStartupError` so activation includes successful initial connection and tool discovery. A failed reload restores the previous bytes or original file absence only while the operation still owns both authorization and file revision. Revisions distinguish a missing patch from an empty file. Failure is confirmed only after the restored worker acknowledges the original MCP entries and the absence of entries introduced by the failed operation. Uncertain restoration remains unknown. Worker start, ensure, and disposal serialize by Profile, including starts already in flight.

MCP removal accepts only `{ "action": "remove", "id": "mcp-name" }` for one existing local MCP row. It reuses Hub’s AST deletion and requires the removed `include:` entry to disappear from the restarted worker before recording success. MCP inventory advertises `mcp_remove: true` when removal is configured; callers must keep removal disabled without that flag. MCP updates accept `{ "action": "update", "id": "mcp-name", "mcpServers": { "name": {} } }` with a complete replacement configuration for exactly that existing name. They reuse Hub’s row update and the same restart acknowledgement and compensation. The `mcp_update` flag gates this operation. Explicit SSE and unknown transport types are rejected before Hub conversion.

The internal [Skill executor](src/profile-skill-executor.ts) reuses Hub’s pinned Markdown renderer to create one new `skills/<name>/SKILL.md` under a Host-resolved Profile. It rejects existing names, unsafe filesystem entries, and concurrent publication; files are private and fsynced. Success requires the supplied runtime acknowledgement callback to return an invocation-neutral definition from the selected preset scope. The executor checks its Profile path, source, name, description, routing guidance, body and invocation flags against the published Markdown; an empty acknowledgement cannot confirm success. Startup registers both installers in one Profile queue. Skill publication restarts the worker and reads `skills/inspectProfile` with the Host-held cookie; that endpoint mounts the default standing preset without a Session or project cwd. Confirmation proves default-preset visibility, not visibility in every custom preset or project. Reconciliation of partial publication remains outside this component.

Skill invocation changes reuse Hub’s AST updater with filesystem effects removed from the generated helper. The Host accepts only an existing local entry ID, a literal `model`/`user` string selector and a boolean; it atomically replaces the Markdown, preserves other metadata and resources, and checks the default preset after restart. Failed acknowledgement restores the original bytes only while revision and authority remain valid, then verifies restoration. Inventory exposes file-derived `model_invocable` and `user_invocable` flags without instruction content; these describe local configuration, not visibility in every preset. The `skill_invocation` capability controls whether Desktop enables the switches.

Markdown file import accepts `{ name, markdown }` and preserves original bytes, metadata and invocation flags. The declared name must match valid frontmatter; description, body, invocation types and payload size are checked before confirmation. The complete JSON plan stays within 32,768 UTF-8 bytes and the body within 24,576 bytes. Existing names are refused. `skill_files` advertises this new-file path; it does not permit ZIP upload or reading a caller-supplied local path.

The [archive installer](src/skill-archive.ts) accepts a public GitHub codeload URL, selected subdirectory and SHA-256 digest from Main’s downloaded preview. It downloads again without redirects and verifies that digest before creating files. It preserves original Markdown, resource bytes and owner-executable scripts without executing them; all resources participate in revision checks and post-acknowledgement verification. Archives are limited to 50 MiB compressed, 512 entries, 10 MiB per file and 100 MiB expanded; traversal, links, case collisions, ambiguous skill roots and mismatched names are rejected. Skill inventory advertises `skill_archives: true` only when the executor is configured for this flow. ClawHub, local archive upload and arbitrary download hosts are unsupported.

The internal [plugin command runner](src/plugin-command.ts) reuses Hub’s pinned argument builder with explicit Node, CLI and pnpm paths. It supplies a private shim, the selected Profile home and the operating-system user home for shared package caches; ambient environment credentials are not forwarded. It disables lifecycle scripts, drains output without recording it, and terminates the process group on cancellation, lease revocation or a two-minute timeout. CLI exit is not activation acknowledgement. Startup registers the bundle executor when a packaged pnpm path is supplied; lifecycle scripts remain disabled and build approval is not exposed.

The internal [plugin executor](src/profile-plugin-executor.ts) binds an immutable source and package name to the selected Profile, refuses replacement of declared packages, and fingerprints root/Profile manifests, locks, build policy, registry configuration and patches. It records success only after the Host-provided bundle acknowledgement and an unchanged post-install revision. Partial installation and failed activation remain unknown; package-manager files are not rolled back or replayed automatically. Startup restarts the selected worker and checks changed enabled root rows against its authenticated plugin inventory. Empty, shadowed, removed, grouped or conditional contributions cannot establish this acknowledgement and leave an unknown receipt.

The optional `pnpmEntrypointPath` startup field receives the packaged command path through `DSH_HOST_PNPM_ENTRYPOINT`. Startup validates this artifact and registers plugin operations only when the field is present; older embeddings retain MCP and Skill operations.

The optional `bundledPluginsRoot` startup field receives, through `DSH_HOST_BUNDLED_PLUGINS_ROOT`, an embedding directory holding `catalog.v1.json` and plugin archives. The exact-schema catalog pins each archive's name, version, SHA-256, source commit and inserted root entry IDs; embedding files must be owned by the Host user or root and must not be group- or world-writable. A missing or damaged catalog only disables `bundled:<name>@<version>` sources; it never blocks startup. The [bundled source](src/bundled-plugins.ts) passes the same confirmation, receipt and activation acknowledgement as other plugin sources. Validation refuses an identity absent from the catalog and any archive whose entry IDs already occur in the Profile's composed entries. Installation re-hashes the archive and copies it without replacement to the content-addressed `profiles/web/.bundled-plugins/<sha256>.tgz`. It installs that Profile-relative file offline-first without lifecycle scripts, so the recorded dependency is `file:.bundled-plugins/<sha256>.tgz` and survives Profile relocation and application replacement.

The opt-in [live worker probe](tests/plugin-worker-live.spec.ts) requires the built CLI, Client packages and Web assets. With `HOST_PLUGIN_LIVE_WORKER=1` and `SLARK_PLUGIN_ACCEPTANCE_ROOT`, the [plugin integration fixture](tests/plugin-command-integration.spec.ts) also drives the real Slark broker, local endpoint, Desktop coordinator and receipt journal through a Unix socket, installs from a loopback registry, restarts the shipped Web worker, and verifies its authenticated inventory and a newer worker generation. The fixture substitutes catalog preflight, confirmation and OS peer attestation; it does not certify native approval clicks or the signed application.

The Windows receipt store uses the existing private-file bindings to atomically replace a bounded collection. Every read verifies SID ownership, protected DACL, link count and reparse evidence; malformed or oversized data rejects access instead of becoming an empty history. The shared operation owner converts interrupted records to unknown without replay. Windows startup enables MCP when the embedding supplies a positive `maximumExtensionReceiptBytes`; omission leaves extensions unavailable. The configured startup exposes MCP inventory, install, update, removal and explicit recovery, and quiesces operations before disposing workers and releasing the Host lock.

MCP configuration parsing and runtime acknowledgement share one executor across POSIX and Windows storage adapters. The Windows startup artifact bundles YAML’s ESM distribution so verified bytes can load from a data URL without package lookup or a file-based CommonJS loader. Windows storage verifies private Profile directories and file evidence, preserves exclusive operation backups, and distinguishes a missing patch from an empty patch during recovery. Deletion compares expected bytes and verifies SID/DACL evidence on the same exclusive native handle before a final authority check and handle disposition; it never reopens the path for deletion. Before launching a Profile with MCP enabled, Host creates missing private web directories and its initial patch. Restarts preserve custom patch contents up to the MCP byte limit. Existing paths with unsafe or inherited permissions are rejected without repair; migration of those existing Profiles remains separate.

## Runtime invariants

`profile.collaboration_delivery` captures the currently authorized Account worker on its first fragment and rechecks that worker and Account on every fragment and after persistence. Across connections the Host reserves at most four uploads and 4 MiB, expires uploads after 30 seconds and retains reservations until cancelled writes settle. It signs only a matching durable original-Profile descriptor; reconnect retries recover the Profile's first commit. The client verifies the signature, Account, process, complete immutable body digest and progress offsets. Unix and Windows startup advertise this capability only when the private receiver is installed; cloud acknowledgement remains a separate operation.

No runtime invariant companion is published: filesystem and wire commit points validate owned state, while lease and crash behavior are covered by integration tests.

The Web worker factory generates and reserves an independent `DSH_PROFILE_REFERENCE_TOKEN` for its parent-only `captureCollaborationReferenceSelection` handle. Selection JSON and returned metadata each permit at most 32 KiB; the request times out after 15 seconds and rejects stopped workers, redirects and cancellation. The handle returns untrusted JSON without content bytes. The parent must validate the computed metadata against its authorized selection before transfer; this handle establishes neither sharing intent nor a Host control-protocol command.

`profile.source_authority` resolves this connection’s verified Account Profile and reads a committed Source descriptor through the supervisor and a dedicated random worker token. Startup installs this reader on macOS and Windows. Missing readers omit the capability; replaced workers, mismatched coordinates/digest, expired challenges or changed Account grants refuse signing. The client verifies the exact challenge, pinned installation/process and Source signature. This operation neither captures a message nor prepares a model; cloud consumption and chat dispatch remain separate.

`profile.reference_authority` is advertised only when both the committed Source reader and `readCollaborationReferenceGrant` are installed. The Host requires a current token-verified Account, compares the independent Profile grant with the requested Source and full reference reservation digest, then rereads the Source before signing. Revocation, expiry, cancellation or changed Profile/Source observations refuse signing. The client verifies the exact challenge and installed peer signature; Source signatures cannot substitute.

`profile.reference_capture` resolves the current Account Profile and reads its Source before invoking the separately token-protected worker capture. It rechecks Account/Profile and the complete Source digest after capture and before returning metadata. The client bounds the operation to 18 seconds and pins the inspected peer; supervisor replacement, disposal, expiry, cancellation and lost ownership withhold results. The shared macOS/Windows startup readers install this operation. Main still establishes sharing intent and validates the computed request before separate reference signing or transfer.

`profile.reference_content` uses the current Account Profile and independent Reference worker capability. Each chunk rechecks actual selected content, Account ownership, worker generation and the committed Source. The client pins the original Account and captured descriptor/request/content metadata, checks every offset and length, and verifies the complete SHA-256 before returning exact bytes within an 18-second operation. Empty content is supported. Cloud transfer and recipient-task access require separate authorization.

`profile.source_snapshot` uses the same current Account and Profile worker reader to transfer original journal content privately. The worker bearer route validates the complete persisted Source, while the supervisor rejects disposed or replaced workers. Fixed 32 KiB byte chunks preserve the existing control-frame budget; the client checks coordinates, consistent descriptor/length, complete UTF-8, cancellation and the inspected peer across a bounded read. It returns original content and redacted model/commit metadata, without credentials, model preparation or a restored call. Startup composes the reader on macOS and Windows; real chat capture and dispatch remain separate.

The Web worker factory creates a separate random `DSH_PROFILE_ANALYSIS_TOKEN`, reserves it against caller environment overrides and keeps it outside view leases. Its Parent-only `collaborationAnalysis` handle sends bounded prepare/dispatch JSON to the private worker, rejects stopped workers and redirects, and validates the complete bounded UTF-8 response. The Parent must derive the original Account/Host binding digest and keep that authority current; this handle alone does not grant cloud authority or install a chat entry.

The Web worker factory separately generates and reserves `DSH_PROFILE_DELIVERY_TOKEN` for its parent-only `receiveCollaborationDelivery` handle. Complete delivery JSON is bounded to 1 MiB; the owning Profile validates its schema and returns at most 8 KiB of untrusted local commit JSON without echoing the answer. Stopped workers, redirects, cancellation and malformed responses reject. The capability stays outside view leases. The parent must authenticate the account namespace and readable cloud projection; this private HTTP handle grants neither signed cloud acknowledgement nor a control-protocol upload. Large replies require an authenticated chunked transfer within the existing control-frame limit.

### Remote workspace directories

The remote directory chooser runs on the Host display. A selected directory receives a Profile-local confirmation bound to the paired client; `workspace.create` consumes it once within 60 seconds and refuses a different path or client. Cancellation returns no confirmation, and picker confirmations are not journaled. The Host advertises `profile.remote_session.directory_picker` only with the worker command executor installed.

## Known Limitations and Deferred Work

The startup compositions relay reference-grant reads to the original current Profile worker. Grants require a separately committed selection and independently revalidated message or attachment bytes. Natural-language selection production and cloud content upload are not connected; an embedding must complete those consumers before enabling reference transfer.

- **Extension support is executor-specific** — `profile.extensions` accepts inventory, prepare, commit, status, and cancel through a live view lease. Plugin execution requires the configured pnpm artifact. The Windows startup composition supports explicitly enabled MCP; Windows Plugin and Skill executors remain unavailable. The embedding must enable and pin this composition before users receive the capability. Skill inventory uses `transport: markdown` and bounded file-derived identifiers. Desktop must reopen the same Profile view after an installation or restored configuration restarts its worker. Packaged-runtime pinning, full Profile migration preservation, process-kill recovery, and unknown-receipt reconciliation require separate end-to-end validation before release.

- **Unlock material remains embedding-owned** — Slark Main must keep the random 32-byte Profile material in macOS Keychain/safeStorage and provide it only across the authenticated Main-to-Host path. It must never enter Renderer, argv, environment, logs, or the registration file.
- **Account access remains session-bound** — Slark Main must obtain the `dsh-host` token from DSH Account and provide it only across the authenticated Main-to-Host path. The Host does not persist or log this credential; an expired token requires Slark Main to refresh the Account session before `profile.ensure` can succeed.
- **Legacy migration is fail-closed until complete** — the Host advertises export only when the active Profile's complete owner-only bundle (sessions, settings, credentials, workspace and Profile configuration) can be staged. A digest-only or session-only transfer is not advertised as a safe migration.
- **Legacy home settings and credentials have no account owner** — export from the fixed OS-user `.dsh` home transfers sessions and workspace. All settings and credentials, including permission, onboarding, model routes and the default model, remain at their original paths. Their source digest detects changes between inventory and transfer. A new Person Profile cannot use those values until an explicit account claim is implemented; migration of already activated Profile data is a separate compatibility case.
- **Legacy claim inventory remains internal and redacted** — Host can inspect the same validated source for DeepSeek, configured pi-ai routes, and DeepSeek web search. It reports candidate ids, credential presence, shared-reference status, a source digest, and counts of unmapped settings and credential records. It does not return secret values or reference names. This inspection grants no claim authority and does not change either source or target; the authenticated claim transaction is still required.
- **Legacy claim storage and startup fence stay inside Host** — the state machine validates secret-free reservation, commit, and verified-restoration events. Unix owner-private and Windows SID-private adapters atomically replace a bounded global snapshot before publishing each state change. An uncertain replacement rejects further writes until reload. Each Profile has a separate private pending marker; both startup compositions check only that Profile's marker before starting its worker, so a damaged global ledger does not take down unrelated DSH Profiles. The macOS claim transaction writes and clears this marker around verified target credential writes.
- **Legacy claim recovery snapshots stay inside the target Profile** — an operation-specific owner-private or SID-private file records both original documents and digests of both projected results. A repeated operation cannot replace its original snapshot, and restoration is allowed only while current documents match the original or projected bytes. Snapshots contain credentials and never cross Desktop IPC. The transaction persists a snapshot before writing either document and removes it after a verified terminal outcome.
- **Provider projection is Host-internal** — the validated legacy reader can return source-bound private documents to Host code, and the projection copies only one confirmed DeepSeek, pi-ai, or web-search route into a target document pair. It derives a unique Profile and operation-bound credential reference, preserves existing personal routes, strips a literal web-search key from settings, and never imports an unrelated provider, grant record, or legacy default model. DeepSeek and pi-ai routes with embedded secret fields or custom headers require manual configuration instead of copying those values into settings. The macOS claim transaction invokes this projection after confirmation.
- **Target document writes remain Host-internal** — the target writer projects one provider from validated source documents onto the current mutable settings and credential files, records both originals before modification, supports retry after either file was written, and verifies the completed pair. Restoration refuses any later personal edit. macOS resolves the active materialized generation; Windows resolves the SID-private `owner-state` files. The macOS claim transaction stops the worker, fences that Profile, checks the source digest, reserves ledger ownership, and invokes this writer.
- **Claim coordination remains Host-internal** — the coordinator serializes one Profile's claims, stops its worker, snapshots original documents, reserves single-owner provider attribution, marks the Profile pending, publishes and verifies both live documents, commits the ledger, clears the marker, restarts the worker, then compares and deletes the secret-bearing snapshot. A committed retry verifies target digests without rereading the legacy source; an interrupted restoration can finish clearing its marker. The macOS control API invokes this coordinator under Account-view authorization.
- **Account claim authorization is separate from ordinary view access** — the Host can resolve a claim target only through a live Main-owned lease for an Account Profile on a connection that successfully verified an Account token through `profile.ensure`. Vault-only restore, offline recovery, local Profiles, owner revocation, and stale leases do not authorize a claim. Inventory, confirmation, and each macOS transaction effect use this check; pending-claim recovery uses a separate same-Account proof.
- **Legacy model inventory is read-only** — a macOS Host whose legacy source is declared quiescent advertises `profile.model_claim_inventory`, `profile.model_claim_confirm`, `profile.model_claim_apply`, and `profile.model_claim_retry`. Inventory returns only redacted candidate metadata. Confirmation rechecks the Account lease, source digest, and credential presence, then issues a one-use authority valid for 60 seconds on the same connection. Apply consumes it before the claim transaction. Retry requires a fresh same-Account proof and the exact reserved candidate, operation id, and source digest. Windows omits these capabilities until its native source inventory is complete.
- **Claim recovery inventory survives view failure** — the macOS Host enumerates only pending ledger reservations and the operation named by an uncleared Profile marker after verifying the current Account token, binding, and vault proof. It returns bounded receipts without reading source credentials or starting the Profile worker. A committed or restored marker can be finished through the existing retry or restore operation.

Confirmed Markdown replacement accepts `{ action: "replace", id, markdown }` under the separate `skill_replace` capability. The exact flat/bundle ID and frontmatter name must match an owned existing entry. It reuses atomic invocation publication, preserves directory resources, and compensates failed acknowledgement while revision and authority remain valid. Success requires the new definition in the default preset; restoring bytes without runtime confirmation cannot report a clean failure.

Confirmed Skill removal accepts `{ action: "remove", id }` with `skill_remove` support. The Host moves the exact owned file or bundle to a private Profile-local holding path, reloads the default preset, and only then deletes the held resources. A matching old path cannot confirm removal. Success persists a bounded `skillSource`: `absent` or the observed replacement source; it does not claim that every same-name Skill disappeared. Failed observation restores the entire entry only while revision, authority and held bytes remain valid, then verifies restoration. Conflicts retain the holding entry and an unknown receipt for reconciliation without overwriting another author.

The internal [bundle toggle planner](src/plugin-toggle-plan.ts) uses app-boot composition to control independently inserted root entries. Shared reconfiguration, grouped or conditional contributions, missing bundles and conflicting later overrides are refused. The plugin executor accepts a confirmed `{ action: "toggle", packageName, enabled }` only when planning and acknowledgement are configured. It atomically publishes the Profile patch, preserves tagged values and comments, and restores the original patch on failed acknowledgement while revision and authority remain valid. Startup restarts the worker; disabled acknowledgement requires the exact configured module with `enabled: false` and no fiber. Package dependencies remain installed. Desktop uses explicit plugin_toggle capability and per-entry configuration states to enable native-confirmed toggles.

Plugin inventory reports optional `plugin_state` as `enabled`, `disabled`, `mixed` or `unsupported`. These states describe composed configuration, not current fiber health. Both directions must be independently plannable before a row is controllable; older or unsupported rows keep disabled buttons. The live CLI/worker/Slark fixture installs once, toggles off and on through three fresh worker generations, and verifies source-bound receipt recovery plus each inventory change. The Electron fixture separately verifies renderer/preload/dispatcher behavior with injected providers.

Confirmed plugin updates use `{ action: "update", packageName, spec }` and the existing exact-source add command. Only dependency-managed, independently enabled bundles can be updated; disabled, mixed and unsupported compositions must not silently gain enabled contributions. Main locks the selected source through Hub preflight and requires its package name to match the existing row. The CLI must publish the requested version, and a fresh worker must acknowledge its contributions before success. Partial dependency changes retain unknown receipts rather than pretending to roll back.

Plugin installation preflight reads the immutable npm version manifest or exact GitHub commit manifest without writing the selected Profile. It returns only recognized lifecycle script names and their exact commands, bound to the source and exact package version by a SHA-256 digest. Lifecycle scripts remain disabled when that list is empty or Desktop omits or changes the digest. A matching second confirmation persists only the reviewed `package@version` in `allowBuilds` and runs the pinned add command without `--ignore-scripts`; unrelated build packages remain denied. Manifest identity drift, redirects, oversized metadata and policy conflicts fail closed before package-manager effects.

Confirmed removal uses `{ action: "remove", packageName }`, accepts only dependency-managed independent bundles, and invokes the pinned CLI remove command. pnpm 11.7 requires `--config.ignore-scripts=true` on remove; the add-only `--ignore-scripts` spelling is rejected. After manifest and bundle registration are absent, the Host removes standalone `{ id, disabled }` overrides for the former contribution IDs, retaining other configuration, then requires all corresponding runtime IDs to disappear. Template bundles are not removable. Removal, repair and unapproved install/update paths keep lifecycle scripts disabled.

Skill inventory joins owned local entries with the current worker’s authenticated `skills/profileCatalog` snapshot without restarting it. Local revision changes during the read, incomplete snapshots, duplicate winning names, and more than 128 combined entries reject the read. Entries expose bounded source categories and `effective`, `shadowed`, or `not_visible` status; a shadowed local entry names its winning source. External winners use opaque `catalog-` IDs and are read-only in Desktop. Provider paths remain inside Host. This inventory includes owned local definitions and default-preset winners, not every losing external candidate or project-specific preset.

Skill removal checkpoints are persisted inside the private operation receipt before moving an entry. The checkpoint binds the exact flat/bundle ID, original content digest, before/expected-after local revisions, and removal/restoration verification stage to the original operation and Profile. The holding name derives from the operation UUID; an existing holding entry is never replaced. Checkpoint storage failure prevents the initial move. A crash may leave the last persisted stage behind the filesystem, so checkpoints are evidence for later reconciliation, not permission to claim success or automatically restore. The ordinary wire receipt omits these Host-private fields.

Confirmed Skill recovery uses the ordinary Skill prepare payload `{ action: "restore-removal", operationId }`, referencing an unknown removal receipt in the same Profile. Host validates the original checkpoint, exact backup digest, target occupancy, and before/removed revisions; the plan also binds the checkpoint digest. Recovery has its own durable UUID and a `restores` link to the original receipt before filesystem changes. It either moves the verified backup back or re-verifies already-restored identical bytes, then acknowledges the default-preset definition. A successful linked receipt releases the original removal and related interrupted recovery attempts from the unknown-operation fence without rewriting their historical outcomes. Unrelated unknown operations remain blocking. Missing legacy checkpoints and conflicts cannot be guessed away. This recovery is limited to Skill removal; it does not restore other Skill edits or plugin package-manager effects.


MCP operations persist a private, exclusive-create backup before recording a checkpoint and publishing the patch. The checkpoint contains before/after revisions, original file presence, introduced entry IDs, and a monotonic stage; it carries no configuration bytes. A backup is at most 1 MiB plus a presence byte, owned by the Host user, mode 0600, and single-linked. Backups remain retained with operation evidence; this interface provides no automatic retention cleanup.

An unknown MCP receipt with recovery evidence advertises `mcp_restore: true`. The ordinary MCP prepare payload `{ action: "restore-config", operationId }` binds a new confirmation to the original checkpoint and current composite revision. Recovery accepts only the recorded after revision or the exact already-restored before revision, preserves original file absence, and verifies the original runtime entries and disappearance of introduced entries. Missing, changed, linked or public backups and concurrent patch edits reject recovery. A linked successful receipt releases the related unknown-operation fence without rewriting historical outcomes. MCP recovery restores configuration only; subprocess and remote-service side effects are outside its scope.

Plugin activation changes persist an operation-owned private patch backup and a checkpoint binding the package name, backup digest, before/after dependency-state revisions, and stage. An unknown toggle receipt advertises `plugin_restore` with its package name. The plugin prepare payload `{ action: "restore-toggle", operationId }` creates a new confirmed recovery operation. Host accepts only the recorded before/after state, verifies that substituting the original patch exactly reproduces the before revision, and reconstructs the original active/disabled contribution expectations from the installed bundle. Changed manifests, locks, policy files or overrides reject recovery; missing, modified or public backups reject it too. Recovery restores original file absence and acknowledges the original worker state without invoking the package manager. It preserves historical outcomes and links the successful recovery receipt. Backups remain retained with evidence. This operation covers activation changes only; partial installation, update and removal effects remain unknown.

Plugin package operations persist their immutable install/update/remove intent before invoking the command runner. Evidence contains the exact requested source, a digest of the original dependency reference, a digest of unrelated manifest/policy/override state, original removal IDs and a monotonic stage. Action and stage fields must be literal strings; arrays and objects are rejected without coercion. Original dependency references and configuration bodies are not stored in receipts. Private receipts accept at most 64 KiB, with matching write and read bounds, to retain bounded bundle removal IDs. Unknown original receipts with evidence may advertise `plugin_complete` for a separately confirmed `{ action: "complete-package", operationId }` plan. The plan binds current revisions, including lockfiles, and the original intent digest; no client-supplied replacement source is accepted.

Completion preserves unrelated dependency declarations, bundle order, policy files and overrides, and accepts only the absent target, its original dependency digest, or the exact requested target reference. Unrelated changes reject preparation and are checked again after commands. Partial lockfile changes are excluded from the unrelated-state digest because command interruption can legitimately change resolution; the full current lock revision is still bound before confirmation and commit. Installation and update rerun the original pinned add command with lifecycle scripts disabled. Removal reruns remove while the dependency exists; when it is already absent, the fixed CLI `plugin --profile web install --no-frozen-lockfile --ignore-scripts` repairs the current manifest’s dependency graph, after which Host removes only the recorded target’s stale bundle registration and standalone activation overrides. Runtime acknowledgement and stable final revisions are required. Another interrupted completion remains unknown and needs another explicit confirmation.

Successful completion uses `completes_operation` and `completed_by`, distinct from restoration links. The original operation and related interrupted completion receipts retain their historical unknown outcomes; their common write fence is released only by a linked successful receipt. Completion requires an authorized Profile lease and intact intent evidence. It neither reconstructs missing legacy intent nor guarantees recovery of a Profile that cannot establish a lease, an invalid manifest, an unavailable package source, or external plugin side effects.

The Unix Host control method `profile.collaboration_analysis` checks the connection’s token-verified Account identity and current Profile before and after prepare/dispatch. The Host derives the preparation binding from that connection, Account, Profile and installation/process identity; callers cannot supply it. The supervisor rejects replies from replaced worker generations. Original output uses bounded base64url so 32 KiB JSON remains within the existing 64 KiB control frame. After the worker saves output, the Host signs its raw JSON digest, dispatch grant and current Account/installation/process identity. Failed saves or changed authorization produce no signed result. Cancellation closes the original operation; the signature binds the saved output to its original dispatch and current Account and Host, and does not establish task semantics or Agent execution authority.

The same current Account/Profile checks cover `capture_reply` and `prepare_clarification`. Host-derived binding is retained through reply capture, complete-input preparation and dispatch; the client validates each action's passive or prepared result category. The client admits output only for dispatch and verifies any signed receipt against that dispatch. Neither operation changes view leases, grants cloud authority or admits tasks.


`attestRootAuthority` requests `profile.root_authority` only when advertised by the peer. The authority resolves the currently verified Account Profile, reads its original root descriptor through the worker supervisor, compares every root/source/command/digest field and rechecks the Account grant before signing. The client verifies the exact challenge, current installation/process, expiry and dedicated root signature. Both startup compositions install the reader; replaced workers, absent roots, mismatched coordinates, revocation and cancellation refuse signing. Worker root metadata uses the private Source-read token and is never included in a browser view lease. This proves a committed root binding; it neither submits a root nor grants execution or acknowledges cloud admission.

Root journal operations retain the authenticated Account binding and Host peer, check authorization before and after worker access, and discard replies from replaced worker generations. The worker uses its private analysis/write token for `/internal/desktop-root-journal`; the Source-read token cannot acknowledge admission. Losing an acknowledgement leaves reconciliation necessary, even if the original receipt was saved.

Root-aware workers advertise `profile.root_analysis` explicitly. Root preparation uses the current Account-authorized Profile and the same Host binding as dispatch; clients refuse older peers before issuing the new command. Unix and Windows startup wire the same root-aware worker owner. Source-only analysis remains separate, without a fallback from root preparation.

Saved-output reads require the separate `profile.root_analysis_recovery` capability. They retain current Account/Profile authorization before and after worker access and use the private analysis token. Older workers reject the command; saved grant metadata never starts another model call.

`rootLookupSupported` advertises `profile.root_lookup` independently of preparation support. `recover_root` uses the same current Account/Profile checks and private worker token as analysis, but accepts only recovered metadata; older peers reject before lookup.

`rootPendingLookupSupported` separately advertises `profile.root_pending_lookup` for `reconcile_root`. It permits only recovered metadata under current Account/Profile authorization.

`rootLiveResumeSupported` advertises `profile.root_live_resume` for the current worker. The Parent derives a resume identity from the Account authorization version, Profile and Host process, excluding only the socket owner. A successful worker handoff replaces the dispatch owner after current Account/Profile checks; it cannot restore an executable call after worker restart.

`attestRootPlanningAttemptAuthority` requires a separately advertised capability. The authority advertises it only when `inspectRootPlanningAttempt` is installed. This private reader must validate current Profile membership, a live preparation and the durable current unused attempt; missing, replaced, dispatched, expired or uncertain records reject. The authority supplies only original Source/root lookup coordinates and the attempt ID, compares every returned input/model/predecessor/root field, and rechecks Account authorization after the read. The client verifies the exact challenge, current peer, expiry and dedicated signature. The proof grants no model dispatch or task execution.

Both startup compositions install the fresh-attempt reader through the worker supervisor and analysis-token HTTP client. Attestation and preparation use the same parent-derived Account/Profile/Host/connection digest; another connection cannot sign or dispatch that live preparation. The supervisor rejects replies after worker replacement, disposal or cancellation. Preparation and dispatch require the separate `profile.root_planning_attempt` capability; attestation also requires its dedicated reader. These operations do not issue a cloud replacement transaction or task execution authority.

`profile.root_planning_attempt_recovery` enables the read-only `read_root_attempt` command. The client checks this capability before sending; the Host resolves the current token-verified Account Profile and checks authorization around the private worker read. The response binds the requested original root and Source and remains evidence only, including after dispatch expiry.

The separately advertised `profile.root_execution_journal` capability forwards bounded concrete execution journal operations only through the current authenticated Account Profile. Host derives the connection binding and rechecks ownership after the worker response. Client and authority both reject an absent capability. The worker uses its private analysis token; journal reads or writes provide no model dispatch, new execution grant or Session-consumption acknowledgment.

`profile.root_feedback` is advertised only with its private Profile receiver. Client and authority check this capability, and Account ownership is revalidated after each bounded feedback response. The parent remains responsible for current cloud result visibility and explicit consumption intent; transport success is not a signed cloud consumption acknowledgment.

For persisted consumer evidence returned by `root_feedback`, the Host verifies the original namespace, delivery and Source coordinates before signing a separate consumption receipt. It uses current Account and installation/process metadata and rechecks the current Profile authority after the worker reply. The receipt contains no answer text and grants no new continuation.

macOS and Windows bind root journal, source inspection and planning-attempt inspection through the same worker operations, while each authority protocol retains its own signed payload.
