# Agent Note: Windows carrier for the single Desktop Host

Status: proposed

English | [中文](2026-09-11-windows-desktop-host-carrier.zh.md)

## Problem

The [single Host control protocol](../../implemented/architecture/2026-09-02-single-host-control-protocol.md) owns one machine-local DSH authority, but its implemented carrier is Unix-domain only. A Windows Desktop package cannot claim that authority by translating the socket path into an ordinary named pipe. A same-user process can otherwise connect first or impersonate the broker unless the pipe, connected process, executable image, and release identity form one verified chain.

Windows upgrades also expose a product-level failure mode outside the transport. Desktop must not treat an unavailable legacy profile as proof that DSH itself is unavailable. A failed migration must preserve the source and permit an explicit isolated local profile, while the Host transport continues to fail closed on untrusted peers.

## Proposal

The Desktop Host package will own one Windows x64 carrier as a platform adapter. It will derive an opaque named-pipe name from installation and endpoint registrations, create one owner-only first-instance pipe that rejects remote clients, and perform blocking pipe operations only in a dedicated Worker. The existing control-protocol codec remains the only wire vocabulary.

The parent and Worker will share a persistent atomic stop flag. The Worker will hand the parent a real current-thread handle with only `THREAD_TERMINATE` access; shutdown will set the flag, retry `CancelSynchronousIo` until Worker exit is confirmed, and only then close that handle. A bounded unconfirmed stop retains the handle and escalates to the Host process supervisor. This closes the no-pending-I/O cancellation race without reporting a stuck Worker as stopped.

The Worker handshake is generation-bound and accepts exactly one ready message containing that cancellation handle. Each attested pipe connection maps to one parent-owned Host session through a UUID and strictly increasing request sequence. Only canonical control-protocol frames may cross the structured-clone boundary, only one request may be in flight, and every response must match its connection, sequence, request ID, and method. Any malformed, duplicate, replayed, or cross-connection message poisons that Worker generation and revokes the active session.

Unix sockets and Windows pipes use the same post-attestation Host control session. That session owns the first `host.inspect`, process-bound one-use authorization, correlated response enforcement, connection cancellation, and owner revocation. A carrier supplies only authenticated frames and transports the returned response; it cannot define a platform-specific account, Profile, migration, or authorization dispatcher.

Shutdown first makes the shared stop flag visible and revokes the active session, then invokes delivery of a generation-bound stop message before dispatching abort callbacks or waiting for session cleanup. This wakes a Worker waiting for a parent response while `CancelSynchronousIo` wakes one blocked in native pipe I/O. Late responses from an aborted session are suppressed, so neither shutdown path can revive a revoked connection.

The Worker runner subscribes to parent control before opening native resources. If stop wins startup, it reports stopped without opening a pipe or cancellation handle. If ready delivery fails after opening the thread handle, the Worker closes that still-unhanded handle itself; after successful delivery, only the parent may close it once Worker completion is confirmed. The runner opens a Host bridge connection only after peer attestation succeeds and closes every pipe through the common native lifecycle.

The parent supervisor applies injected, abortable deadlines to the ready handshake, pre-handoff exit, and session cleanup. Every readiness failure enters the same idempotent stop path; a normal or failed Worker exit after ready also enters that path so the transferred handle cannot leak. Session cleanup is observed independently from native cancellation: malformed input revokes the session immediately, but a blocked `close` cannot postpone `CancelSynchronousIo`. If bounded cancellation cannot prove exit, the result remains `still_running` for the process-level fallback instead of requesting a reboot or claiming success.

The parent spawns only a file-backed Worker with an empty `execArgv` and a strictly decoded generation, pipe policy, shared stop buffer, publisher anchors, and executable digests. A Worker `error` poisons the generation and starts cancellation immediately, but only the later `exit` event confirms completion and permits handle release. If that exit arrives after a bounded `still_running` result, the retained handle is closed then and the observable supervisor state advances to stopped.

The Worker composition root decodes boot data before loading Koffi or any native authority component. A stop flag already visible at entry produces one generation-bound stopped event with zero native loads. Otherwise cancellation, lifecycle, blocking I/O, and the complete peer attestor load as one fail-closed set before the runner starts; no partial native chain can serve a pipe.

The parent carrier publishes the existing secret-free registration v1 only after the Worker ready promise resolves and its live state is still `ready`; on Windows the compatible `socket_path` field carries the derived named-pipe path. It checks readiness again after atomic publication so a failure during the write cannot be returned as a successful start. Construction, readiness, or publication failure enters the same bounded close path. A failure reported after start is owned exactly once by the carrier and immediately starts shutdown. If stop throws or remains `still_running`, the carrier notifies the embedding to terminate the Host process and rejects close; it never reports quiescence or asks the user to reboot. A Worker factory that throws must be all-or-nothing and must not leave an unowned live Worker.

The parent resolves its Windows user SID from the current process token instead of accepting identity from the embedding. Its registration root, lock, temporary publication, and final registration are opened through stable handles that reject reparse substitution and path redirection. Every object must be singly linked, owned by that SID, and carry a protected full-control DACL containing exactly the user, LocalSystem, and Builtin Administrators; the three ACEs inherit to both child objects and containers so Profile and migration plugins cannot fall back to the process default DACL. Registration publication uses a same-directory flushed temporary file, write-through replacement, and a second stable-handle verification. Single-Host ownership is a non-shared writable file handle, not a PID cleanup protocol: process death releases it automatically and a live sharing violation is a conflict. The lock is acquired before Profile registry or command-journal initialization and is released only after the pipe Worker, every authenticated session, and every Profile child are confirmed quiescent. Any unconfirmed stop or lock release requires Host process termination and never opens the lease for a second Host.

The Profile registry accepts one cohesive platform file authority, so Windows registry reads and replacements reuse the same stable private-file evidence while the POSIX path remains unchanged. Its maximum snapshot size is injected by startup configuration. A Windows Web Profile also cannot report an arbitrary loopback URL: the Host queries `GetExtendedTcpTable` for IPv4 listening rows and requires exactly one `127.0.0.1:<port>` owner whose PID is the child it just started before exchanging the one-use bootstrap token.

Windows startup can prepare a local isolated Profile without enabling migration capabilities. It creates only missing files with create-new semantics, preserves safe mutable settings, credentials, workspace, and plugin content on retry, and requires an exact Host-owned patch. The command journal uses bounded stable reads and atomic replacement under the single-Host lease. Neither authority accepts a legacy source path, so migration absence or failure cannot write `%USERPROFILE%\.dsh`, block local DSH, or impersonate a completed migration.

Cordis startup dispatches explicitly by platform. Windows private identity contents are never environment values: a signed, non-exported bootstrap artifact creates the device key and Ed25519 installation key through SID-pinned create-new files, recovers a concurrent creator by rereading the stable winner, and emits only public installation metadata. The account verification keyring is passed to that child on bounded stdin, persisted beneath the isolated environment root with the same ACL authority, and rechecked by digest. Host startup then acquires the single-instance kernel lease before rereading those exact private files. Any outside-root path, partial identity, public/private mismatch, generation conflict, malformed UTF-8, or ACL/reparse drift fails closed without touching legacy data.

The standalone Main-only client artifact also owns Windows discovery. It first recomputes the opaque pipe path from the trusted installation and endpoint registrations, then connects through Node's named-pipe client and uses the existing fresh `host.inspect` challenge. The Host installation key, installation id, and executable digest must all match the embedding-owned anchors. A missing registration-owned pipe is `stopped`; a path mismatch, failed challenge, malformed protocol, or other ambiguity is `unknown`. The pipe server independently authenticates the connected daemon through SID, Authenticode publisher, and stable executable digest, so neither direction relies on a path alone.

After connection, the Worker will read the pipe client PID twice around opening a query-limited process handle. It will compare the process token owner with the Host token owner, open the executable for read while denying write and delete sharing, and compare both process-image reads with the final handle path by Windows ordinal rules. It will then require both a pinned Authenticode leaf-certificate SHA-256 and a pinned streaming executable SHA-256 from that same stable handle.

WinTrust verification will be noninteractive and cache-only. It will keep one `WINTRUST_DATA` record from `WTD_STATEACTION_VERIFY` through `WTD_STATEACTION_CLOSE`; only status zero succeeds. Executable hashing will use 64 KiB chunks and reject files above 512 MiB, premature EOF, zero progress, or changing native lengths.

The carrier stays unexported. The package ships the Worker as a dedicated file-backed bundle so the parent starts it without eval or a data URL; that artifact is deliberately absent from package exports. Slark Desktop hashes, packages, and orchestrates the adapter, while account, environment, migration, fallback, release enablement, and capability-discovery policy remain outside deepseek-harness.

The Main local-vault adapter and Host carrier load a single canonical Koffi addon by independently pinned digest rather than its JavaScript package wrapper. The parent passes the same pin to SID resolution, protected registration files, Profile-listener attestation, and cancellation. Strict Worker boot data carries the pin across the thread boundary; the Worker independently verifies it before loading cancellation, pipe lifecycle, pipe I/O, executable hashing, Authenticode, or peer-process bindings. The embedding must keep the addon immutable throughout load and use; the helper does not establish that authority from a path digest.

## Alternatives considered

The native existing-directory inspector is separate from directory preparation: inspection opens only an existing object, reads handle-derived evidence, and closes it on success or failure. Reusing directory preparation would create a missing source during inventory. Missing-path errors remain errors because absence of one pathname without verified ancestors is not fresh-install authority. Full source enumeration, schema admission, and embedding integration remain outside this primitive; mocked ABI checks do not replace Windows native validation.

**Use Node's public named-pipe server alone.** Node does not expose the accepted server pipe `HANDLE` needed by `GetNamedPipeClientProcessId`. Reading private runtime fields would make the security boundary depend on an undocumented implementation detail.

**Trust the same Windows user SID only.** Any process owned by that user could then issue Host commands. The stable image handle, Authenticode pin, and executable digest are required to distinguish the packaged broker from another same-user process.

**Copy the macOS carrier and migration behavior.** Unix socket ownership, code-signing APIs, launch lifecycle, file replacement, and process identity do not map to Windows. Shared protocol and profile semantics are retained, but platform evidence is implemented separately.

**Enable the carrier before native validation.** Cross-platform unit tests can check state machines and ABI arguments but cannot prove Windows structure layouts, signing behavior, Defender interaction, or installer lifecycle. Capability therefore remains false until native evidence exists.

## Acceptance criteria

The pinned native helper defers default loader construction until path and digest validation, using the exact addon file as its base. The private `windows-startup.js` artifact and file Worker carry that pin through every production native caller without using the Koffi package wrapper. Real Node subprocess tests import verified startup bytes from memory, reject unsupported platforms before native loading, and reach the pin failure without package resolution. Package checks require both private artifacts without public launcher exports. Windows native startup, signed-process validation, and standard-user installer evidence remain required before release enablement.

Directory inspection decodes generic and file-rights SDDL tokens without mapping generic masks into private-file full control. Native Windows ancestor directories can carry those tokens; rejecting them prevents legacy presence checks even when the path is readable. Unknown tokens and overflowing masks remain errors. The isolated Windows administrator probe distinguishes absent, present, missing-parent, and foreign-owner cases with explicitly SID-owned fixtures; it does not establish standard-user installation behavior or migration admission.

The startup artifact exposes the legacy probe loader without eagerly loading native code. Probe and local-vault assembly share SID and pinned-addon loading, while the returned legacy callback captures only the directory inspector. Artifact tests require the export and reject an absent release pin; source tests distinguish assembly from later metadata I/O and reject missing native capabilities. Main orchestration and native Windows execution remain separate validation requirements.

The legacy-home metadata probe exposes observation separately from migration admission. Ancestor inspection and same-user home checks precede the leaf read, but independently closed handles do not prove one stable directory tree. An observed absent leaf therefore cannot bypass explicit fallback admission or authorize source writes. Tests cover each ancestor failing, native error provenance, redirection, invalid paths, and foreign ownership; Windows native and complete schema inventory evidence remain required.

- Native storage tests exercise real SID decoding and typed security-attribute arguments, reopen two stores in one process, reject competing leases, and preserve the prior envelope after an oversized write. Mock-only coverage cannot replace this native gate or the separate standard-user installation gate.
- A Windows x64 Worker test on Windows 10 and 11 proves owner-only pipe creation, connected PID evidence, same-SID enforcement, stable executable acquisition, Authenticode verification, digest pinning, framing, disconnect, and handle cleanup.
- Worker tests prove ready-before-connect startup, generation and connection isolation, sequential request correlation, malformed-message poisoning, response-wait shutdown, and native-I/O shutdown without a leaked session or cancellation handle.
- Shared-session tests prove inspect-first admission, one-use authorization, response correlation, abort-driven owner revocation, and idempotent close through both carrier interfaces.
- Runner tests prove stop-before-start, failed ready handoff cleanup, attestation-before-session order, clean disconnect, malformed parent input, and final native descriptor, pipe, and thread-handle ownership.
- Parent-supervisor tests prove abortable ready deadlines, stop-before-ready completion, early Worker exit, automatic post-ready failure shutdown, cleanup-independent native cancellation, bounded retries, explicit `still_running` escalation, and transferred-handle closure only after confirmed exit.
- Worker-thread and composition tests prove canonical boot data, file-only spawn with empty inherited arguments, immediate error poisoning without premature exit confirmation, late-exit handle recovery, pre-start stop without native loading, and all-or-nothing native composition.
- Package artifact tests prove the file-backed Worker bundle is shipped while no new public package export or Windows capability is exposed.
- Identity artifact tests prove create-new race recovery, retry stability, exact private paths, bounded stdin, key-pair consistency, and a shipped but non-exported bootstrap bundle; no private bytes appear in Cordis environment configuration.
- A malicious same-user client with the wrong signer or digest cannot obtain Host authority, and exact native diagnostics remain local while the public protocol returns a closed authority error.
- Fresh start, concurrent start, upgrade, crash restart, rollback, and shutdown tests prove one Host authority without an orphan pipe, stale registration, reboot loop, or source-data mutation.
- Carrier tests prove registration is published only across a continuously ready Worker, construction and runtime failure are reported once, every startup failure enters bounded cleanup, and unconfirmed cleanup requires process termination rather than reporting success.
- Startup tests prove the kernel lease precedes registry initialization, isolated Profile retries never overwrite mutable content, and lock release follows pipe, session, and Profile-child quiescence.
- Client artifact tests prove Windows discovery recomputes the registration-bound pipe path, authenticates the Host with the shared signed challenge, distinguishes only a genuinely missing trusted pipe as stopped, and remains a standalone builtin-only bundle.
- Slark can explicitly create an isolated local profile after deterministic migration failure without weakening Host peer verification or changing the preserved source.
- Public capability discovery, package exports, downloads, and update metadata remain unchanged until signed Windows artifacts pass native standard-user installation and upgrade validation.
- Existing macOS and protocol tests remain green; no Windows-only account, profile, session, plugin, or wire fork is introduced.

## Risks

WinTrust and Koffi expose pointer-width layouts and cleanup obligations that unit fakes can model incorrectly. Fixed x64 size assertions, real signed and tampered fixtures, and Windows-native CI are mandatory release evidence.

Cache-only verification does not fetch current revocation data. The design accepts that offline trade-off because release authorization also requires an exact executable digest; anchor rotation and revocation response must update the signed release manifest before enabling a new binary.

The 512 MiB digest ceiling can reject a future oversized packaged broker. That limit is an intentional resource boundary; increasing it requires measured artifact evidence and an updated native timeout budget rather than a silent configuration override.
