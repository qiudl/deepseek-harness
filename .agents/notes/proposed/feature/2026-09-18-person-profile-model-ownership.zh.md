# Agent Note: 旧模型凭据归属于 Person Profile

Status: proposed

[English](2026-09-18-person-profile-model-ownership.md) | 中文

## 问题

固定的 OS 用户 `.dsh` 主目录早于经过认证的 Person Profile。其中的凭据和模型设置没有账号归属。将它们导入第一个激活的 Profile，会让该账号在用户未确认时控制所有提供方。独立的 Profile worker 目录和空启动环境能隔离新输入的凭据，却不能纠正旧数据导入。

## 提案

固定旧数据导出器只迁移会话和工作区，全部设置与凭据都留在原处。权限默认值和引导确认也归属于账号；复制它们会在未经确认时改变首个登录账号的行为。导出器读取并校验原始文档，不改写它们，并携带被保留数据的摘要，以便在盘点确认时发现来源并发变更。这样可以阻止新导入静默分配凭据，也不改变普通 Profile 间迁移。

DSH 的模型设置将为已认证 Person Profile 提供按提供方操作的脱敏认领入口。认领会检查来源所有权和代际，将该提供方凭据及对应路由提交到当前 Profile，并在路由可用前记录唯一归属。失败或中断后保留原文件和可重试状态。同一账号可以幂等重试；其他账号收到冲突。已有 Profile 代际中自动导入的旧数据，还需单独的升级迁移，之后 Desktop 才能启用个人模型复用。

### 认领契约

模型设置页经可信 Desktop 桥接调用认领；浏览器只收到候选名称和状态，不接收凭据值或 OS 用户主目录路径。Host 将每个候选绑定到当前已认证账号 Profile、有效的 Main 所持视图租约、来源盘点摘要和短有效期。本地匿名 Profile 和远程浏览器不能认领。无法确认归属的插件或来源映射显示为不可用，不猜测其提供方。

用户确认某个提供方后，Host 先持久预留唯一归属，再写入目标 Profile。写入期间停止该 Profile worker，并在认领未决时阻止其重启。Host 只复制该提供方的路由和凭据到仅账号可读的文件。多个提供方共用的旧凭据引用会改写成该 Profile 内的独立引用，认领一个提供方不会启用另一个。旧来源文件保持不变。Host 校验目标设置和凭据、提交回执后，才重启 worker。崩溃或写入失败留下未决回执；同一账号可重试或依据记录的原文件恢复目标，其他账号收到冲突。界面只报告脱敏进度和错误。

全局唯一归属账本使用原子私有快照，但 worker 启动不能依赖解析这份全局文件。Host 在写入目标前，还须持久标记受影响的 Profile 为未决；只有在目标校验和账本提交后才清除标记。启动时，每个 Profile 只检查自己的标记，再决定是否启动 worker。全局账本损坏时禁用后续认领，无关 DSH Profile 继续工作。macOS 的当前可变文档位于 `migration-owner-state/<generation>/`，Windows 位于 `owner-state/`。macOS 不应写入不可变的 `owner-state.json` 种子，因为后续个人编辑会使它与实际文档不同。

只有在对应提供方已被认领、目标 Profile 尚无个人默认模型时，界面才提供旧默认模型选项；应用它仍需用户明确确认。已有 Profile 代际须按迁移来源检查后才可启用个人模型请求；如果无法区分自动导入值与后来由账号自行修改的值，应保留文件并要求用户明确处理，不能删除或静默信任。处理期间 DSH 工作区、会话及非模型操作仍可使用。

## 考虑过的替代方案

**随工作区迁移所有旧凭据。** 这延续原有行为，但会把没有账号归属的凭据隐式交给首个登录账号。

**传输后删除旧文件。** 这会阻断后续认领，而且迁移中断可能造成永久丢失。原文件应继续作为认领来源。

## 验收标准

- 新的旧数据迁移完成后，两个账号在显式认领前都无法使用旧设置及任何提供方凭据；工作区和会话仍可用。
- 认领一个提供方后，只有确认的账号能使用它；第二个账号无法认领或读取。重复及中断认领均可确定性恢复，且不回显明文。
- 多个提供方共用的旧凭据引用须按认领的提供方重新映射；一次认领不能顺带启用其他提供方。认领中断时，不得以部分写入的目标文档启动 worker。
- 在 Desktop 启用个人模型复用前，已经自动导入凭据的 Profile 代际也完成安全迁移。
- macOS 和 Windows 已安装产物执行相同的账号与来源归属规则。

## 风险

保留模型数据意味着迁移后的 Profile 暂时不能调用旧模型。已有 Profile 代际也可能已经包含导入凭据。认领界面和升级迁移完成前，本提案不能视为完整交付。
