# Agent Note：受管凭据的可选认证加密

状态：已实现

[English](2026-08-29-optional-encrypted-credential-documents.md) | 中文

## 问题

[`credentials-local`](../../../../packages/credentials/credentials-local/README.zh.md) 会刻意避免把提供方凭据放入进程环境，但其受管 YAML 文档仍是明文。仅属主可访问的文件权限可以隔离工作站上的不同用户，却无法保护云部署中的持久化 Cell 状态、快照或备份。Slark 的仅远程 Runtime Cell 需要继续使用既有的 Models 页写入路径，同时加密每用户的持久文档，且不得把 Slark 服务密钥复制进 Harness。

加密模式必须保持可选。若改变默认文档格式，会破坏普通本地安装，还会让旧版回滚程序尝试把密文当作 YAML 解析。

## 决策

`credentials-local` 接受可选的绝对路径 `encryptionKeyFile`。设置后，配置的文档路径保存规范的 `dsh-credentials-encrypted-v1:` 信封，而不是 YAML。每次写入都采用 AES-256-GCM、新的 96 位 nonce、128 位认证标签，以及固定的格式版本关联数据。加载、重载和读-改-写都会先认证解密再解析；格式错误、内容篡改或密钥不匹配会关闭式失败，诊断中不会出现凭据值。

密钥文件包含一个规范的 32 字节 base64url 密钥。POSIX 上它必须是仅属主可访问的普通文件，并且只在插件激活时读取一次。密钥不会复制到插件输出或进程环境；插件销毁时会清零内存缓冲区。密钥交付与备份由部署负责。部署应使用 `.credentials.enc` 等独立密文文件名，分别备份密钥与密文，并在恢复时成对恢复。

Slark 云端 bundle 选择该模式。每个 Runtime Cell 通过 systemd credential 获得独立的部署密钥，隔离的 DSH home 中只写入密文。仅远程 bundle 继续不包含本地 Shell、子进程与文件系统 provider：静态加密无法阻止能够主动读取密文与密钥的同 UID 进程。

## 后果

- Models 引导与 `credentials.set` 仍是唯一用户流程；describe/list 响应仍只披露是否存在及来源，绝不返回值。
- 明文本地安装保持原有路径、格式与热重载行为。
- 加密写入在内存中保留 YAML 语义，但外部编辑器只会看到不透明的认证信封。
- Slark 使用独立的加密文件名，因此旧二进制可以安全回滚。该版本暂时无法使用已保存凭据；恢复支持加密的版本后凭据重新可用。
- 只替换密钥并不等于轮换。必须保留旧密钥，直到文档已明确重新加密，或用户已重新输入凭据。
- 该方案保护持久化状态与备份，但不等于 OS 钥匙串边界。未来若必须隔离同 UID 的恶意代码，可增加平台钥匙串 provider。

## 考虑过的替代方案

**默认加密所有本地凭据文档。** 拒绝，因为它会给每个桌面用户引入密钥管理、改变既有格式，并让回滚语义变得模糊。

**把密钥放进环境变量。** 拒绝，因为环境转储与子进程继承是常见泄露路径；部署已经具备基于文件的 systemd credential 通道。

**用密文覆盖 `.credentials.yaml`。** 拒绝，因为回滚版本会尝试解析加密信封。独立路径会表现为明确的可用性损失，而不是格式混淆。

**复用 Slark 应用或服务密钥。** 拒绝，因为凭据存储一旦失陷就会跨越信任边界，影响 Slark 身份认证或其他用户。每个 Runtime Cell 都接收独立的加密密钥。

**把加密视为对本地 agent 工具的防护。** 拒绝，因为能读取两份文件的同 UID 进程可以完成解密。因此 Slark 云端边界还必须同时使用仅远程工具预设。
