# Agent Note: Profile-bound extension operation receipts

Status: implemented

English | [中文](2026-09-12-profile-extension-receipts.zh.md)

## Problem

REQ-20260912-0004 embeds Desktop Hub markets in Slark. Hub's standalone default directories cannot identify the active Host-managed Person Profile. An interrupted package or configuration write can leave effects even when its caller receives no result.

## Decision

The [operation owner](../../../../packages/host/desktop-host/src/extension-operations.ts) binds confirmation plans to an authorized Profile and its configuration revision. It stores a private, fsync-backed receipt before starting an executor. Receipts omit installation payloads and exception messages because both can contain credentials. Each plan accepts only one operation UUID; retries return its receipt.

The Host resolves extension authority from a live view lease, the current runtime generation, and a connected or local-only writable grant. Offline recovery access is insufficient. Executors receive a live authorization guard and cancellation signal; they must guard each effect and await subprocess quiescence before returning.

Same-Profile jobs serialize. An executor exception has an unknown outcome because it may follow a write. Unknown outcomes block new and already-queued writes to that Profile. A process restart converts unfinished receipts to unknown without replay. Cancellation does not overwrite a success already confirmed by the executor. Disposal aborts accepted work and awaits its settlement before the Host lock can be released.

## Alternatives considered

**Use Hub's default Profile directories.** They refer to the standalone launcher, not the Profile authorized by Slark's current window, and can write to the wrong target.

**Reuse the session command journal unchanged.** Its executor exception path records failure without distinguishing possible partial extension effects, and it lacks the extension cancellation lifecycle.

**Replay unfinished writes.** An absent final receipt does not prove that package installation or a configuration write did not happen. Automatic replay can duplicate or overlap effects.

## Consequences

A real Host lease and real filesystem writes exercise target authorization, duplicate submission, revision conflicts, cancellation, secret-free receipts, and unknown outcomes in the [composition tests](../../../../packages/host/desktop-host/tests/extension-operations.spec.ts). Private receipt reads reject symlinks, hardlinks, insecure permissions, corrupt data, and non-UUID paths.

`UnixHostServer` exposes negotiated, lease-bound extension commands only when an executor is configured. Startup installs the MCP executor, and socket disconnect aborts its accepted operations. [The authenticated socket test](../../../../packages/host/desktop-host/tests/extensions-wire.spec.ts) sends an install, loads its written patch through the real Loader, calls the discovered MCP tool, and receives `pong`. A second authenticated connection can recover the same receipt after proving the same Profile; borrowing another connection's lease fails.

The MCP executor uses the unchanged MIT-licensed Hub source with a reproducible generated ESM copy. Its adapter owns private atomic writes, startup-failure policy, and compensation. It restarts the worker to avoid mistaking an already-active old configuration for the new installation, then waits for active MCP rows through the authenticated worker API. If reload fails, restoring the previous bytes and acknowledging their reload confirms failure; a conflicting edit, revoked grant, or failed restoration leaves the outcome unknown. This restores configuration, not arbitrary effects of an MCP subprocess or remote service.

Worker lifecycle calls serialize by Profile so a concurrent ensure cannot create a second child and disposal cannot miss a pending start. Desktop must reopen its view after worker restart. Plugin execution and a released runtime pin remain absent. Slark development now supplies its broker, local HTTP endpoint, installation coordinator and capability-gated Hub UI. Full Profile migration preservation, process-kill recovery, Windows behavior and manual reconciliation of unknown receipts remain unverified; the change is not a complete M2 release.

## Slark joint acceptance

Set `SLARK_EXTENSION_ACCEPTANCE_ROOT` to the Slark source checkout when running `extensions-wire.spec.ts` to execute its test-only client through the real Slark broker, authenticated HTTP endpoint, Desktop client, Hub installation coordinator and persistent operation hints. The standalone built Host client connects to this test server; the installed MCP tool must return `pong`, reopening invalidates the old context, and another Profile cannot read the receipt. The fixture supplies peer attestation and view activation metadata; it does not test code signing, a packaged desktop, or a real browser worker. Ten consecutive joint runs passed after fixture corrections; an earlier refresh failure was not reproduced and still needs packaged lifecycle validation.

## Skill publication and acknowledgement

The internal Skill executor extracts the unchanged Markdown, ZIP path and GitHub URL parser declarations from pinned Hub source, with reproducible hash checks. It owns Profile resolution and exclusive private publication, while a caller-supplied acknowledgement verifies runtime discovery. This separates reusable Markdown handling from Hub’s standalone directory assumptions. New-skill installation never overwrites existing skills; ambiguous publication or acknowledgement failures retain an unknown receipt and prohibit replay. Partial publication can leave an owned directory requiring reconciliation.

The [Skill composition tests](../../../../packages/host/desktop-host/tests/profile-skill-executor.spec.ts) load the real Cordis skill registry and filesystem provider to verify the installed name, content, source path and invocation flags. They also verify isolation, unsafe paths, concurrent authors, cancellation, and durable unknown outcomes. Startup composes Skill and MCP execution under one revision and operation queue. The Slark market UI enables MCP, new Markdown skills and template installation only when the corresponding Host inventory succeeds; GitHub market archives additionally require explicit `skill_archives` support.

The [runtime observation verifier](../../../../packages/host/desktop-host/src/skill-runtime-ack.ts) rejects a matching name with a different path, source, body, routing metadata or invocation policy. It consumes invocation-neutral definitions because the session command catalog filters out model-only skills. A callback that returns no definition leaves a persistent unknown outcome. The worker endpoint resolves the default standing preset before returning the definition; a global catalog does not prove preset visibility.

The [Skill socket composition test](../../../../packages/host/desktop-host/tests/skills-wire.spec.ts) submits a plan through the authenticated Unix client, writes a Profile skill and reads it over HTTP using generated RPC dispatch, the real default preset and filesystem provider. The definition is absent from the global registry but present in the preset scope. Duplicate submission performs one acknowledgement, another Profile cannot read the receipt, and an intervening MCP edit invalidates a Skill plan. The fixture supplies cookie authentication and peer attestation; native worker launch, browser refresh and packaging still require installed-app validation.

The Skill socket test also accepts `SLARK_EXTENSION_ACCEPTANCE_ROOT`. Its subprocess runs the real Slark broker, local HTTP endpoint, Desktop client, shared installation coordinator and durable UUID journal, then verifies receipt recovery, view-context renewal and Profile isolation. Electron separately exercises Hub create/template buttons and disconnect handling; that fixture does not show the actual Main confirmation dialog or launch a packaged worker.

Main reuses the pinned Hub GitHub URL parser and hashes a bounded download before native confirmation. Host downloads the confirmed URL again and checks the digest, so a changed branch cannot silently replace approved bytes. This keeps archive data outside the 32 KiB control payload while retaining scripts, references and original metadata. It costs a second download; redirects, alternative branches and ClawHub single-file fallbacks are not attempted. Archive validation, exclusive publication and runtime verification belong to the Host executor.

The shared [runtime observer](../../../../packages/host/desktop-host/src/plugin-runtime-ack.ts) requires each expected entry ID to identify one enabled, active row with the exact module name. Failed or duplicate identities reject the acknowledgement; absence, disabled rows and module mismatches remain unconfirmed until cancellation or timeout. MCP supplies its fixed module identity through this observer. Plugin command completion remains separate from this runtime proof, so a package-manager exit code cannot become an installation receipt by itself.

The [official CLI integration fixture](../../../../packages/host/desktop-host/tests/plugin-command-integration.spec.ts) uses `HOST_PLUGIN_ACCEPTANCE_PNPM` to select a real pnpm entrypoint and requires the built DSH CLI. A loopback registry serves one test bundle. The CLI installs it and reconciles the bundle list, then the real profile loader and Cordis runtime mount its layer and produce an activation marker. Its postinstall marker stays absent. This covers local registry installation with pnpm 11.17.0; it does not verify a shipped package-manager artifact, third-party builds or native Desktop confirmation.

The [plugin executor](../../../../packages/host/desktop-host/src/profile-plugin-executor.ts) uses the same persistent operation owner. Its source validation and revision checks precede package-manager writes; activation failure preserves an unknown receipt because a failed install can change several package-manager files. The CLI fixture also exercises duplicate commit suppression and receipt recovery. Startup registers the executor when the embedding supplies pnpm; native confirmation remains embedding-owned.

The [bundle contribution selector](../../../../packages/host/desktop-host/src/plugin-bundle-entries.ts) uses app-boot composition with and without the installed layer, followed by Profile and home overrides. Startup observes changed enabled root rows on a fresh worker using the stable `include:` Loader ID prefix. Missing observable changes, groups, disabled or conditional rows and removed rows remain unconfirmed. This also maps MCP configuration IDs to their actual bootstrap-include runtime IDs. The pnpm startup field selects the optional plugin executor; all configured installers share the composite revision and receipt queue.

The [live plugin wire fixture](../../../../packages/host/desktop-host/tests/plugin-wire-fixture.ts) retains the real package-manager command, signed socket messages, Profile leases, fresh CLI worker and authenticated runtime response. A failed or unchanged worker generation cannot acknowledge installation. The Slark child reopens an extension context to recover the receipt and proves that another Profile cannot read it. External catalog preflight and native consent remain explicit test substitutes. Source-plane clients resolve their TypeScript launcher from the Desktop package that declares it.

MCP removal retains the same prepared-plan revision, lease checks, serial execution and receipt ownership as installation. Hub deletes only a locally declared MCP row; the fresh worker must omit its Loader entry before success. A failed removal acknowledgement restores and acknowledges the original configuration when authorization and revision still permit compensation.

MCP editing replaces one existing named row through Hub’s `updateMcpRow`. Main confirms full replacement, including credential fields, and does not return stored configuration to the market renderer. Renaming, implicit creation, mixed-server updates and unsupported transport declarations are refused. The loader composition test updates to a second MCP endpoint and verifies that subsequent calls reach it rather than the old endpoint.

Skill invocation changes preserve Hub’s field-level AST semantics while the Host owns reads, atomic publication, revision checks and compensation. Model and user flags remain independent. Success requires an invocation-neutral definition from the selected default preset to match the new file; a shadowed or stale definition cannot establish success. Inventory reports local file flags and uses the existing opaque flat/bundle IDs, rather than returning filesystem paths.

Markdown import avoids regenerating source documents through the new-skill form, which would discard metadata outside the form schema. Main decodes bounded selected-file bytes as strict UTF-8 and reuses Hub’s parser; Host independently validates name and metadata, publishes through the existing exclusive new-skill installer, and acknowledges the original content in the default preset. Source paths never cross from the renderer, and new-file import cannot grant overwrite authority.

Same-name Markdown replacement binds a selected opaque entry ID before native confirmation. Main rejects mismatched names, missing entries and unsupported Hosts before preparation. Host independently validates the replacement and uses the existing revision-checked edit/compensation path. Tests cover an unaffected same-name sibling, retained attachments, cancellation without commit, failed acknowledgement restoration, and replacement through the real default-preset HTTP/Unix composition. Archive replacement remains unsupported.

Skill deletion is removal of one owned entry, not erasure of every same-name definition. The existing invocation-neutral default-preset read verifies absence or a different winning source before cleanup. Its bounded source category survives receipt reload and reaches Desktop history. Real HTTP/Unix/Slark composition tests install, update and delete a local skill while retaining an actual user-agents fallback. Concurrent restoration tests preserve a new author and the original held file. A complete live shadow/source inventory and recovery UI remain pending.

Hub manual activation edits inserted module rows, whereas installed DSH bundles also contribute automatic layers. Reusing insert-row deletion alone cannot prove bundle deactivation. The toggle planner therefore identifies independent contributions through the real composition, publishes disabled overrides, and rejects shared modifications. Loader tests exercise enable/disable/enable with actual plugin effects and an unaffected second service. Runtime inventory tests require an exact disabled row with no fiber; executor tests verify byte-exact compensation and unchanged package registration. Desktop toggles and the live CLI worker fixture are connected; signed package acceptance remains pending.

The live cross-repository fixture now installs version 0.0.1, disables/enables it, updates to 0.0.2 whose module writes a different execution marker, and removes it. Five worker restarts and exact runtime inventory checks establish the lifecycle; persistent receipt queries and an empty installed row are separately asserted. Removal initially exposed pnpm 11.7 rejecting --ignore-scripts; the supported configuration option is now regression-tested with lifecycle sentinels. Electron checks update entry/cancel/success and uninstall with injected providers, while native confirmation and authorization are enforced by the Main coordinator. Signed macOS and Windows acceptance remain pending.

MCP recovery requires operation-owned durable bytes because a receipt digest alone cannot reconstruct configuration after interruption. The executor writes its private backup before the immutable checkpoint, then publishes the patch. Recovery binds the checkpoint and current revision to a new confirmation and UUID; stage metadata alone never proves filesystem or runtime state. Original absence is distinct from an empty file, and restoring old entries also requires proof that introduced entries disappeared. Conflicting or unverifiable state remains unknown; successful recovery links historical receipts instead of rewriting them. Tests cover interrupted publication, interrupted acknowledgement and explicit retry, backup integrity, and the real Unix/HTTP/Slark recovery path. OS process-kill and signed application acceptance remain separate.

Plugin activation recovery is separate from package-manager repair because a configuration backup cannot reconstruct an interrupted dependency transaction. The before/after revisions cover manifests, lockfiles, policy files and overrides, including original patch absence. Matching the backup and both revision views prevents restoring stale activation policy over changed dependency state. A new confirmed operation restores or rechecks the original patch, then observes both active and disabled contributions on a restarted worker. The live CLI/Slark fixture interrupts the third toggle after checkpoint publication, restores it without an extra package installation, then updates and removes the plugin. Fault injection verifies the recovery protocol; it is not an OS process-kill or signed-package acceptance test.

A partial package transaction is completed toward its original requested state rather than described as a rollback. Durable pre-command intent fixes the package, action and source; unrelated inputs are hashed, while the original dependency reference is retained only as a digest. A new confirmation binds the present full revision before any retry. Lockfiles can contain legitimate partial writes, so they bind the current plan but are not treated as an immutable before-state boundary. The original intent constrains targets and Host checks unrelated inputs again after commands. A dependency already removed from the manifest requires dependency-graph repair and target-only bundle reconciliation, since replaying remove alone cannot repair the CLI’s missing before-dependency membership. Completion links remain distinct from restoration links and do not rewrite original outcomes. The real CLI/worker/Slark fixture confirms interrupted install, update and removal, with scripts disabled; separately injected runtime failures verify explicit retry of an unknown completion.

Windows receipts use a single bounded private collection because the native registration bindings expose verified atomic file replacement, not directory enumeration. `ProfileExtensionOperations` consumes the same read/write/list store interface on both platforms. Collection validation rejects duplicate operation IDs, unknown fields, malformed UTF-8, and size overflow before publication; no retention policy silently removes unresolved operations. The caller holds the single Host lease throughout read-modify-write. Native Windows installation and executor integration remain separate acceptance work.

MCP storage now separates POSIX file permissions from Windows SID/DACL enforcement while retaining shared Hub conversion, revision digests, durable checkpoint validation and runtime acknowledgement. Windows restoration preserves original file absence through a bounded, byte-matching exclusive handle operation using Win32 FileDispositionInfo. Missing files, changed contents, unsafe evidence and lost authority reject deletion; native disposition or close failures remain errors. The operation owner can reopen Windows receipts and explicitly restore an unknown operation without replaying installation. Native Windows execution and startup composition remain unverified.
