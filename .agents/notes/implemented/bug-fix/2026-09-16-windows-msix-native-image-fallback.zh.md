# Agent 说明：MSIX 拒绝加载的原生镜像改用已校验副本

状态：已实现

[English](2026-09-16-windows-msix-native-image-fallback.md) | 中文

## 问题

MSIX 安装包给自身的 `.node` 文件授予了 `BUILTIN\Users` 的读取和执行权限，但对它们调用 `LoadLibrary` 仍会失败并返回 `Access is denied`。因此，从侧载的 Slark Store 包启动的每个 `dsh --profile web` worker 都会在插件树加载期间死亡：`sharp` 和 `@koromix/koffi-win32-x64` 都抛出 `ERR_DLOPEN_FAILED`，加载器报告 `plugin tree failed to load`，worker 在打印就绪行之前退出。在 Windows 验收机上针对安装包运行时实测，worker 在 17 秒时退出。

先前的一次尝试把这些包物化到了共享的 profile 模块回退目录下。失败的解析过程从不查询该目录：加载器条目是从安装树导入的，因此 `sharp` 解析到安装包自身的 `node_modules`，并在那里找到它的原生同级模块。profile 层的回退无法拦截一个从未离开安装树的解析。

## 决策

在 `healProfilesModuleFallback` 期间、加载器挂载插件树之前，装上 `process.dlopen` 回退。先尝试安装路径本身。只有被拒绝的加载才会回退：拥有该镜像的整个包——必须是整包，因为原生镜像会按相对路径加载同目录的 DLL——被复制到 `$DSH_HOME/profiles/.dsh-windows-native-modules/<digest>/<package>` 这一内容寻址目录下，然后加载副本。装上回退后，同一个 worker 实测 6.4 秒达到就绪。

先试安装路径带来三个性质。镜像本就能就地加载的普通安装不复制任何东西，也不付出任何代价。不属于任何包、或位于安装树之外的镜像，会原样重新抛出加载器自己的错误。无法发布的副本会抛出同时指明拒绝原因和发布失败原因的错误，因为退回安装路径只会复现原本的 `Access is denied` 并抹掉它的成因。

该回退在每个进程中只安装一次，重复启动时返回同一个 disposer：堆叠的包装层会让每一层各持一份备忘表，并且再也无法恢复原始加载器。

## 测试

`packages/boot/app-boot/tests/profile.spec.ts` 搭建真实的包目录树，以及一个只拒绝 MSIX 所拒绝内容的替身加载器。覆盖：可加载的安装不复制、被拒绝的加载走回退、无法发布的副本同时报告两个成因、无法重定向的镜像原样重抛、被篡改的副本被修复，以及只安装一次。

## 考虑过的替代方案

**把原生包物化到 profile 模块回退目录。** 先前已上线并在此撤回：失败的解析始终停留在安装树内，从不到达 profile 的 `node_modules`。它还在每次启动时对四棵包树做全量哈希却毫无效果。

**无条件重定向安装树下的所有镜像。** 拒绝，因为普通安装会复制它本来就能加载的数十兆原生镜像，还会凭空多出一条失败路径。

**用复制到包外的 Node 运行 worker。** 拒绝：该可执行文件已因无关原因被物化，而这次的拒绝是镜像路径的性质，不是加载进程的性质。

## 后果

加载原生镜像的插件可以在 MSIX 包内工作。启动方在首次回退前，每个包要付出一次被拒绝的 `LoadLibrary`；首次回退会按内容代次复制该包一次。副本位于 Harness home 之下，因此继承 profile 自身的权限，而不是安装包的权限。worker 在其余生命周期内会继续使用它已校验过的物化代次；进程运行中途被篡改的副本要到下次启动才会重新校验。
